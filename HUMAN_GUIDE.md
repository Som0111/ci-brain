# CI Brain — Human Guide

Single reference doc for this project. Updated at the end of every completed phase per `CLAUDE_CODE_PROJECT_RULES.md`.

## What this project does

A backend service that ingests test-run data (JUnit XML from pytest, coverage.py JSON) from
a target Python repo's CI, and will eventually: detect flaky tests statistically, predict the
minimal test subset to run for a code change, and cluster failures by root cause with an
LLM-generated summary. See `CI_Brain_Claude_Code_Roadmap.pdf` for the full phase plan and
locked scope decisions.

## Why the major components exist

- **FastAPI app** (`app/`) — the ingestion/query API everything else is built on.
- **SQLAlchemy models** (`app/models.py`) — `Repo`, `TestCase`, `TestRun`, `TestResult`. This
  is the schema every later phase (flakiness detection, impact analysis, clustering) reads
  from and writes to, so it's deliberately kept minimal and normalized now rather than
  reshaped later.
- **Parsers** (`app/parsers/`) — pure functions, no DB or FastAPI dependency, so they're
  independently unit-testable and reusable by the Phase 2 replay harness.
- **Alembic** (`alembic/`) — schema migrations, hand-written (not autogenerated) for the
  initial migration since there was no live database to diff against when it was written.

## Architecture / design decisions worth knowing

- `TestCase` rows are deduplicated per repo by `(repo_id, node_id)` — re-ingesting the same
  test across multiple runs reuses the same `TestCase` row and just adds new `TestResult`
  rows. This is what makes cross-run analysis (flakiness, impact analysis) possible later.
- `TestRun.coverage_data` stores the raw `coverage json` output as-is (a JSON column). Phase 4
  is what turns accumulated coverage data across runs into the file-to-test dependency graph —
  Phase 1 just stores it.
- Enum columns (`TestRun.source`, `TestResult.status`) use `values_callable` so SQLAlchemy
  writes the enum's lowercase `.value` ("junit", "passed") to Postgres, not the uppercase
  Python member name ("JUNIT", "PASSED"). **This bit us once already** — see Known
  limitations / gotchas below.
- Local test suite (`tests/`) runs against an in-memory SQLite DB, not Postgres, so the test
  suite has zero external dependencies and runs in under a second.

## How to run it locally

1. Postgres must be running with a `ci_brain` database and user (see setup steps already
   walked through — native PostgreSQL 18 install, database/user created via `SQL Shell (psql)`).
2. From `C:\Users\USER\projects\ci-brain`:
   ```
   .venv\Scripts\python.exe -m alembic upgrade head      # apply migrations (only needed once, or after new migrations are added)
   .venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
   ```
3. API is at `http://127.0.0.1:8000`. `/health` should return `{"status":"ok"}`.

## How to test it

```
.venv\Scripts\python.exe -m pytest -q
```
No Postgres needed — tests use in-memory SQLite (see `tests/conftest.py`).

## Known limitations / gotchas

- **SQLite vs Postgres divergence bit us once**: the enum bug above (`values_callable`) only
  showed up when testing against real Postgres — SQLite has no native enum type, so it
  silently accepted whatever string SQLAlchemy sent. If something works in `pytest` but fails
  against the real API, suspect a SQLite/Postgres behavioral difference first.
- `coverage_json` ingestion is currently stored but not validated beyond "has a `files` key" —
  no per-test coverage-context parsing yet. That's Phase 4's job.
- No auth on any endpoint — fine for a local/portfolio project, not fine for anything public.
- Ingestion endpoint currently identifies a run only by `repo_id` path param; there's no
  idempotency/dedup if the same JUnit file is POSTed twice (it'll create a second `TestRun`).

## Troubleshooting notes

- `sqlalchemy.exc.OperationalError: no such table` in tests → the SQLite in-memory test DB
  needs `poolclass=StaticPool`, otherwise each new connection gets its own throwaway database.
  Already fixed in `tests/conftest.py`; noting it here in case it resurfaces in a future test file.
- Getting `Internal Server Error` back with no detail from a running `uvicorn` process → check
  `uvicorn`'s own console/log output, not just the HTTP response; FastAPI doesn't leak
  traceback details to the client by default.
